# item 53：治理 qa-busy-day-plan e2e 偶发失败

日期：2026-11-24
分支：`xiaolai/qa-e2e-flake-53`（自 master `9d0143c`）
范围：`e2e/qa-busy-day-plan.spec.ts`、`e2e/fixtures/fake-codex.mjs`。没有改动任何产品代码；诊断期的临时插桩（`butler-service.ts` 的 finish 延时、fixture 的 trace 落盘、probe spec）已全部移除。

## 1. 根因结论与证据

两个历史失败（P1 合并后 `:144` 平常日、item 51 合并后 `:169` 钉死 45 分钟）属于同一类问题：**规格文件在真实状态就绪之前就断言/输入**，不是产品逻辑错误。

### 1a. 任务断言读盘太早，且把读错误吞成“0 件任务”

旧 helper `tasksWrittenForDate` 在「生成计划」工具行出现后立刻读一次 vault。工具行只在 `runTool` 返回后才渲染，说明 `writeFileAtomic`（临时文件 + rename）已经返回；但在 Windows 上，刚 rename 完的文件对读者仍可能短暂返回 `EBUSY`/`EPERM`/`EACCES`。旧实现的 `.catch(() => null)` 把这类错误当成“文件不存在”，于是测试看到 0 件任务并失败。

证据（受控实验，脚本在 %TEMP%/lock-demo，未入库）：

- 用 `FileShare.None` 持有句柄模拟刚写好的文件：旧读法返回 `[]`，`rawError.code === 'EBUSY'`，即错误被吞掉；释放后同一目录能读到 `2026-11-24.md`。
- 轮询读法在 `polledAfterMs: 2866` 时读到同一文件，`newImmediateError: 'EBUSY'`。说明“立即读失败、稍后读成功”是稳定的可复现机制，而不是猜测。
- 产品自己对这类错误就是按瞬时处理的（`writeFileAtomic` 内部 rename 重试 20 × 10ms），且工具行出现即代表写入已返回，所以这是**读者侧**的同步问题，不是产品丢写。

### 1b. 第二轮发送落在上一轮 run 的 settle 窗口里，草稿被丢

旧流程在模型确认文本出现后立即 `fill(request)` + `click(发送)`。此时上一轮 run 可能仍在 settle：`typing = activeRun && isActiveRun`，`finish()` 先持久化 assistant 再发 `done`，settleRun → `complete()` → refresh/reload，`showWelcome` 翻转会让 ChatPane 在两处 Composer 渲染点之间切换，textarea 被卸载/重挂；`submitComposer` 在 `conversations.selecting || hasActive` 时也会拒绝。若输入/点击跨过这次 React commit，草稿会丢，发送按钮保持 disabled。

证据：

- 重负载下拿到了真实的旧规格失败（%TEMP%/flake-probe-run1/1795504007970-fail-pinned.json）：`locator.click: Timeout 30000ms`，locator 解析到 `<button disabled aria-label="发送">`；composer 为空；页面上没有「停止生成」；fake 模型 trace 只有 create-ask/create-result，**没有 plan-ask**——请求根本没发出去，而不是产品没执行计划。
- 页内 50ms 采样（%TEMP%/flake-probe/composer-log.jsonl）：settle 时刻 textarea 的 DOM 节点标识从 `1` 变 `2`（重挂），草稿在状态更新落地时保留、点击后清空且「停止生成」出现——即失败仅发生在“更新落地前点击”的窄窗口。
- 用临时 `STUDY_COACH_E2E_FINISH_DELAY_MS=3000` 放大 settle 窗口：旧流程单测仍通过、日志显示草稿存活；加固后的流程 15/15 通过（1.6m）。说明这是提交竞态，而非确定性产品缺陷；产品侧“settle 期间丢弃草稿”属交互边角，本次不动产品代码，由规格在真实状态上同步规避。

### 1c. 顺带消除的潜在午夜缺陷

旧规格在测试开头取一次 `localDate(new Date())`，播种和读任务时又各取一次 `new Date()`；应用在工具执行时再取一次当天。跨午夜时三者可能得到不同日期（P1 合并提交时间 2026-11-24 00:00:30 +0800，正是高概率时段）。现在每个测试只取一次 `today`，用它播种、读盘，并硬断言写出的那天 `=== localDate(today)`，跨午夜时明确失败而不是静默读错文件。

## 2. 改动清单与理由

`e2e/qa-busy-day-plan.spec.ts`

- `readdirOrMissing` / `readFileOrMissing`：只把 `ENOENT` 当“还没有”，其他错误原样抛出（交给 `toPass` 重试，持续失败时报真实错误，不再伪装成 0 件任务）。
- 新增 `workspaceDirs` / `readWorkspaceName` / `workspaceNamed`（用 `parseWorkspaceFile` 读 workspace.md）、`plannedDays` / `plannedDayOfPlan`（按项目名读 `tasks/YYYY-MM-DD.md`）：建项目和写任务都以磁盘真实状态为同步点。
- `sendMessage`：`toPass` 只重试“输入→草稿粘住且发送可用”，成功后点击，并等「停止生成」出现，证明 run 真的开始了。这是状态等待，不是测试重试；下游断言没有放宽。
- `createProjectThenAskToPlan`：先轮询磁盘确认「考研」存在，再等确认文案，再等「停止生成」消失（上一轮 run 结束），最后才发计划请求——把 1b 的竞态窗口变成明确的等待。
- 每个测试只取一次 `today`；`plannedDayOfPlan` 断言写入日 == `localDate(today)`（1c）。
- 原有 6 条验收断言全部保留（满日：行明细 10 分钟/一周安排 + 恰好 1 件 + ≤10 分钟 + 今日页可见；平常日：120 分钟/默认值 + 30 分钟；钉死：45 分钟/本次指定 + 1 件），并给平常日/钉死补了 `pageerror` 断言。可用性读取为零仍由 `qa-busy-day-tool.spec.ts` 计数桩钉住，未改动。
- 未加 test retries（playwright 配置 retries 0 未动），未弱化任何断言。

`e2e/fixtures/fake-codex.mjs`

- 新增 `toolResultPayload(name)`：解析实际工具结果 JSON；`create_workspace` 的确认文本只在结果里有 `workspaceId`（兼容 `{workspaceId}` 与 `{ok,result:{workspaceId}}` 两种形状）时回复「已创建项目「考研」…」，失败回复「项目没有建成，请再试一次。」。理由是规格把确认文案当作建项目成功的可见证据，fake 不能无条件声称成功，否则会掩盖工具失败。
