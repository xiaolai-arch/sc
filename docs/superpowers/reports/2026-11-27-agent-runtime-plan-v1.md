# ASAKI 自研 Agent 底座方案 v1

**建议立项自研 `ASAKI Agent Runtime`，用 Pi 做第一版可替换的执行引擎。** 我们自己定义一次任务怎样开始和结束、模型能看到哪些数据、工具在什么条件下可以写入、失败后如何恢复。Pi 负责它已经做得好的部分：驱动模型调用工具、把工具结果送回模型、输出流式事件。第一版不 fork Pi，也不引入完整的 Pi Coding Agent。

判断这个底座是不是我们的，有一个实际标准：**以后移除 Pi，ASAKI 的界面、领域工具、用户数据和验收用例都不需要改，只需要换一个执行适配器。** 这条比“自己写了多少行循环”更值得作为架构验收标准。

## 一、先定产品边界

第一版为 **ASAKI 桌面端的个人管家**服务，不做通用编程助手，也不先做一个供外部开发者使用的平台。用三类任务把底座做实：

| 首批任务 | 检验底座的什么能力 | 用户能看见的结果 |
|---|---|---|
| **安排今天的计划** | 能否读取正确项目和日期，调用现有 planner，而不是让模型重写业务规则 | 满日只排 1 件、最多 10 分钟；用户明确给了 30 分钟，则以用户输入为准 |
| **把一条承诺改到周五** | 能否选中正确记录、校验日期、可靠写入，区分“准备修改”和“已经修改” | 改期后，详情和通知中心看到同一个日期；无效日期不写盘 |
| **总结这一周** | 能否以只读权限跨项目取必要事实，并区分用户记录与模型推断 | 复盘能指出结论来自哪条记录；没有记录就说明没有，不编补 |

顺序是**先计划，再改期，最后复盘**。三个场景分别逼出工具调用、可靠写入、上下文管理的问题。第一版不做多 Agent 协作、插件市场、任意 shell、全库向量化或自动后台写入。团队里六个 Orca bot 是研发分工，不必复制到用户的桌面产品里。

## 二、总体架构：五层，一条写入路径

| 层 | 我们要建或保留什么 | 明确不让它做什么 |
|---|---|---|
| **① 交互层**：Electron Renderer | 展示回答、引用、待确认操作和执行结果；支持取消与重连 | 不持有模型密钥，不直接写 vault，不从模型文字推断“保存成功” |
| **② 运行时**：ASAKI Runtime | 管理 `sessionId`、`runId`、状态、预算、取消、确认和事件顺序 | 不定义“满日排多久”“承诺能改到哪天”等业务规则 |
| **③ 执行适配器**：Pi / Legacy / Fake | Pi 驱动新引擎；Legacy 包装现有管家用于对照与回滚；Fake 在测试里稳定制造失败 | Pi 的消息类型、错误类型和会话文件格式不得进入 UI 或 vault |
| **④ 工具网关**：Tool Gateway | 解析参数、绑定当前用户和项目范围、检查权限、去重，再调用业务服务 | 模型不能自授权限；不能给模型开放通用文件写入来绕过服务 |
| **⑤ 领域与存储**：现有 ASAKI 服务 | planner、commitments、reminders 等继续拥有业务约束；vault 保存用户可直接阅读的事实 | 不依赖 Pi，不把聊天记录当作第二份任务或承诺数据库 |

**一次真实调用应该这样走：**用户说“把周三那条承诺改到周五” → Runtime 固定本次参考日期和时区 → Pi 请求查找承诺 → 工具网关只返回匹配的必要字段 → 如果有两条同名承诺，先让用户选 → `commitments` 服务校验并写入 → UI 收到业务服务的成功回执才显示“已改期”。

这里有两个值得保住的设计：**当前时间由一次运行统一提供**，防止工具与 planner 在午夜两侧各算一个“今天”；**业务结果以服务回执为准**，即使模型提前说了“改好了”，界面也不会把它当作提交成功。

建议立项做 **ASAKI Agent Runtime（ASAKI 智能体运行时）**：由我们定义运行协议、工具权限、上下文、数据和评测标准，第一代引擎采用 Pi。**自研的验收标准是：将来拔掉 Pi，ASAKI 的业务工具不用重写，用户数据不用迁移，桌面端也不用跟着换。**

                                       ▼

| 模块 | 自研职责 | 明确不做 |
|---|---|---|
| **运行内核** | 定义一次运行如何发起、等待确认、取消、结束和恢复；对桌面端提供稳定事件 | 不把 Pi 的事件类型、消息类型直接暴露给界面 |
| **引擎适配层** | 把我们的请求转换给 Pi，把流式文本、工具请求和错误映射回来；保留旧引擎 | 不让业务代码到处 `import pi`；不在 Pi 外面再写一套竞争的工具循环 |
| **上下文与记忆** | 决定本次能读取哪个项目、需要哪几条事实、哪些能发给模型 | 不把整个 vault、所有历史会话或其他项目笔记塞进提示词 |
| **工具与权限** | 统一登记工具、验证参数、校验项目范围、确认副作用、记录执行结果 | 不把 shell、通用文件写入或任意目录读取交给学习管家 |
| **领域服务** | 继续决定满日排多久、什么日期有效、承诺怎么改、何时算保存成功 | 不把已经用代码和测试保证的规则搬回提示词 |

**运行位置：**第一版放在 Electron 主进程侧，沿用现有领域服务；renderer 只收事件和展示确认，不持有模型密钥，也不直接写 vault。先不拆独立守护进程、不开本地 HTTP 端口。以后真要做独立 CLI 或真实 Web 客户端，再让它们实现同一套请求协议。当前 Web 预览的 mock 可以测交互，不能证明真实写入安全。

首选 [`@earendil-works/pi-agent-core`](https://github.com/earendil-works/pi/tree/main/packages/agent)，不引入完整 Coding Agent。官方核心包已经提供带状态的工具执行循环、事件流和上下文转换入口，适合放在适配层里。**第一阶段用固定版本的依赖，不直接 fork，也不复制上游源码改名。**

## 二、先定三份自己的接口，再接 SDK

这三份接口是底座最值得长期维护的部分。以下是**拟定的 ASAKI 契约**，不是 Pi 的 API。

| 契约 | 第一版必需内容 | 为什么由我们定义 |
|---|---|---|
| `RunRequest` | `runId`、`sessionId`、发起来源、项目范围、用户输入、引擎选择、预算、取消信号 | 用户在聊天里说「改到周五」，和后台晨检读到同一句话，权限不能一样 |
| `ToolSpec` | 工具名及版本、输入与输出 schema、副作用类别、需要的权限、是否支持预览和去重 | 模型只负责提议动作，不能靠生成参数给自己提权 |
| `RunEvent` | `run.started`、`text.delta`、`approval.requested`、`tool.committed`、`tool.failed`、`run.finished` 等；带运行 ID 和递增序号 | UI 能区分「正在尝试」「已经落盘」「需要你处理」，换引擎也不用重写 |

建议只开放窄接口，例如 `plan_workspace`、`list_due_commitments`、`reschedule_commitment`，不提供一个

## 一、架构：一套底座，两个可替换引擎

```text
桌面管家 / 晨检 / 周复盘
          │ 统一任务入口：目标、项目、触发来源、用户授权
          ▼
ASAKI Agent Runtime                         我们自研
  ├─ RunController     任务状态、取消、超时、预算、恢复
  ├─ ContextBuilder    本轮需要哪些事实，哪些允许发给模型
  ├─ ToolGateway       工具注册、参数校验、权限、确认、执行回执
  ├─ SessionJournal    本地运行记录、操作编号、恢复所需的信息
  └─ EnginePort        只暴露 ASAKI 自己的事件和调用协议
           ├─ LegacyEngine：封装现有管家，作对照和回退
           └─ PiEngine：接 pi-agent-core，作首选新实现

所有引擎调用工具，都只能走：
ToolGateway → ASAKI 领域服务 → 本地 vault
```

**运行位置**：首版在 Electron 主进程内做逻辑隔离，沿用现有 IPC。渲染层只负责开始、取消、确认和展示，不持有模型密钥，也不能直接执行工具。先不拆常驻服务：我们目前更需要验证执行协议，而不是引入另一套进程通信和部署。以后若需要独立 Web 后端或后台常驻进程，可以搬运行位置，不改上层协议。

**数据边界**：vault 仍是任务、承诺、忙日和计划的唯一事实来源。运行日志回答“Agent 做过什么”，不回答“用户现在有哪些任务”。晨检和周复盘重新读领域服务，不把昨天的聊天摘要当成今天的事实。

## 二、哪些必须自己写，哪些直接用 Pi

| 模块 | 选择 | 关键理由 |
|---|---|---|
| 模型调用、工具循环、流式事件 | 首版复用 Pi，由 `PiEngine` 翻译事件 | 没必要重写通用循环；只有适配器允许导入 Pi 包。 |
| 模型供应商接入 | 首轮保留现有配置，只打通一个已配置、支持工具调用的模型 | 不同时迁移执行引擎和所有 provider，否则失败时分不清是哪层的问题。后续再逐个验证云端和本地模型。 |
| 工具及业务规则 | 自研；包装现有 service，不重写业务 | `plan_workspace` 必须走已验证的忙日规则；承诺改期必须走 service 的真实日期校验，不能靠 prompt。 |
| 权限、审批、取消和写入回执 | 自研，放在工具网关 | 能否修改用户数据，不由模型或引擎决定。 |
| 上下文、记忆和隐私 | 自研 | 哪些项目可见、哪些内容可出机、用户忘记某条信息后如何生效，都是产品承诺。 |
| 通用终端、任意文件编辑、第三方插件、子 Agent | 首版不接 | 学习管家不需要 shell 才能排计划。先把一个 Agent 做可靠，再决定要不要增加权限和复杂度。 |

### 第一轮就测「我今天特别忙，帮我安排一下」

选它是因为我们刚修过一个典型问题：同一份忙日记录，从一个入口排计划会生效，从另一个入口却不会。这个场景既能测 Pi 会不会用工具，也能测它有没有绕过业务规则。用同一个模型、同一份临时 vault，让现有管家和 Pi 各跑一遍：

- **忙日和普通日**：忙日从真实管家入口只排 1 件、不超过 10 分钟；普通日不被限成 10 分钟。以最终计划为准，不以回复里说了什么为准。
- **用户明确说「今天有 30 分钟」**：显式时长优先。Pi 不应在提示词里自己重算一遍规则。
- **工具失败或中途取消**：不能没排成却回复「已安排」，也不能重试后多出一份计划；关掉 Pi 的开关，原管家仍可用。

这轮要走**真实主进程和临时 vault**。现在的 Web 预览用的是 mock 后端，适合看交互，不足以证明新引擎真的把事办成了。除正确性外，顺手对比完成一次任务的耗时、模型调用次数，以及为了接 Pi 到底删掉了多少自维护代码。

**我的取舍：先作为独立技术验证，不插进 iter32 的交付线。** 如果它通过上述场景，又确实减少了我们维护工具循环的工作，再接第二个场景「承诺改期」；如果只是把现有模型层包了一层，就停在原型。只有遇到能复现、且公开扩展接口解决不了的问题，才值得维护自己的 fork。
